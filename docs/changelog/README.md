# История изменений YANIME

Файл `yanime.json` — основной источник курируемой истории версий YANIME.
Для каждой версии добавляйте отдельный объект в массив `releases`.

## Принцип чистой истории коммитов

История Git должна показывать законченные пользовательские обновления, а не ход отладки.

- Один коммит — одно самостоятельное важное изменение, которое имеет смысл показать пользователю отдельно.
- Промежуточные исправления, тесты, локализация, импорты, форматирование и рефакторинг объединяются с коммитом соответствующей функции.
- Несвязанные пользовательские возможности не объединяются в один общий коммит.
- Служебные изменения оформляются тегами INTERNAL, CORE, CHORE или DOCS и не должны засорять историю «Что нового».
- Перед публикацией проверяйте, что заголовок коммита понятен без знания внутренней реализации.

## Обычные записи

Поле `notes` содержит короткие пользовательские изменения. Пишите по-русски,
начинайте с результата для пользователя и избегайте внутренних технических
подробностей. Один пункт — одно самостоятельное изменение.

## Привязка записи к коммиту

Если пункт относится к конкретному коммиту, добавьте его в
`commit_overrides` внутри объекта нужной версии:

```json
{
  "sha": "98adb1e156b357f665ae35c3be4d6ffdda19154e",
  "tag": "UI",
  "title": "Фильтр серий: сохранение выбранного режима и позиции списка",
  "description": "Выбранный режим сохраняется между запусками приложения. При переключении фильтров список возвращается к той же серии."
}
```

- `sha` — полный SHA коммита из GitHub, без URL.
- `tag` — исходный тег коммита без квадратных скобок. Не переименовывайте его.
- `title` — новая формулировка вместо исходного заголовка коммита.
- `description` — необязательное короткое пояснение; можно опустить.

Такой текст заменяет заголовок и описание исходного коммита в автоматически
собираемой истории и карточке релиза GitHub. В приложении он отображается
в истории версии, к которой привязан. Тег коммита сохраняется.

## Стиль текста

Ориентируйтесь на реальные коммиты Helandy: `[ТЕГ] Область (платформа): суть изменения`.
Префикс — в квадратных скобках и верхнем регистре, описание — по-русски, короткое и предметное.
Область указывайте, когда она помогает понять изменение: `Плеер:`, `Расписание:`,
`Библиотека:`; платформу — как `(мобилка)` или `(ТВ)`. Точку в конце заголовка не ставьте.

Основные теги: `FEATURE`, `BUGFIX`, `UI`, `CORE`, `MOBILE`, `TV`, `TEST`, `CI`,
`DOCS`, `RELEASE`. Тег `INTERNAL` оставляйте только для технических изменений,
которые не нужно показывать пользователям.

## Что попадает в пользовательскую историю

- `docs/changelog/yanime.json` — курируемый источник заметок YANIME по версиям. Для новой
  версии добавляйте отдельный объект в `releases`; формулируйте пункты как заметные результаты
  для пользователя.
- `commit_overrides` используйте, когда заголовок или описание конкретного коммита нужно
  уточнить для истории релиза. В `tag` указывается тег без квадратных скобок.
- Генератор `.github/scripts/update_release_history.py` автоматически исключает коммиты
  `[INTERNAL]` из пользовательской истории. Не добавляйте внутренние рефакторинги и техническое
  обслуживание в `notes`.
- Если изменение ещё не выпущено, не придумывайте номер версии заранее: добавьте его в
  соответствующий объект при подготовке релиза.
